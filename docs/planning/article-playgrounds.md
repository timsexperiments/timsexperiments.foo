Provide labeled fields and an editable JSON textarea for the same Person record. This is an executable browser exercise with editable input. It does not execute visitor JavaScript. This is the recommended first stage, replacing the earlier recommendation to require QuickJS immediately. It agrees with `docs/planning/campus-experience.md`, sections "One content and interaction model" and "First article challenge", and `docs/planning/campus-build-plan.md`, step 4 of "Ordered coding tasks and ownership". It produces a useful instrument while arbitrary-code isolation remains unproved. The broader request for runnable article examples remains open if editable code, rather than data, is essential to the first delivery.

Keep the challenge independently usable as ordinary HTML. The campus is an optional entrance and visual representation of its results. It must never gate Writing, Experience, Resume, Contact, or reading. `CONTEXT.md` defines article challenges separately from optional minigames. The latest `docs/3d-site-transformation.md` sets the freelance/fractional audience, cinematic campus, accessibility, browser execution, and no-paid-services requirements; this proposal does not settle its camera or device choices.

Include one challenge, Run, Stop, Reset, named checks, a static worked explanation, and graceful runtime failure. Exclude terminals, arbitrary schemas, npm installation, Go/C# execution, file uploads, persistence, shared snippets, accounts, external requests, timing races, and leaderboards. No paid service or remote execution is needed.

## Supported input and encoding rules

Freeze these rules before writing check fixtures:

1. Accept exactly one JSON object with all four own fields `name`, `age`, `email`, `hobbies`. Reject unknown keys, missing fields, nulls, nested objects, non-string text fields, and non-string hobby entries. Reject special keys such as `__proto__` as unknown; construct a fresh Person explicitly rather than merging parsed objects into application state. Do not coerce numbers or strings.
2. Age is a finite integer in the signed int32 range, -2147483648 through 2147483647. Negative values are permitted for encoding experiments and explained as a schema capability, not a realistic age. Reject decimals, out-of-range values, and overflow-to-infinity JSON numbers. Normalize negative zero to zero before encoding and comparison.
3. Preserve text, whitespace within strings, repeated hobby order, and duplicate hobbies. Do not trim, Unicode-normalize, or validate email delivery. Reject lone UTF-16 surrogates in decoded strings so UTF-8 conversion cannot silently change a supported input. Emoji and combining characters are valid.
4. Proposed bounds are 16,384 UTF-8 bytes of raw JSON text, 1,024 UTF-8 bytes per string, and 32 hobbies. Bound raw text by code-unit length before allocating its UTF-8 representation, then enforce its byte limit before JSON parsing. Apply field/count bounds before encoding. These are product limits, not browser-process memory quotas.
5. Keep the fields form and JSON as two views of one draft. Apply JSON to fields only after complete validation. Do not overwrite invalid JSON when switching views; explain the error and retain the draft. Editing either valid view invalidates the previous result. Reset explicitly discards edits and restores the starter, with confirmation if edited.
6. Create the normalized record in the fixed order name, age, email, hobbies. JSON output is compact `JSON.stringify` of that record, including all four fields. Measure `new TextEncoder().encode(jsonText).byteLength`, then decode those actual bytes and parse them for the JSON round trip. Editor indentation and JSON escape spelling do not count toward output size. TextEncoder produces UTF-8 bytes. [Encoding standard](https://encoding.spec.whatwg.org/#interface-textencoder)
7. Encode binary Protobuf using the article's exact Person schema, without a delimited-message length prefix. Use a generated static encoder and decoder bundled with a pinned minimal runtime. protobuf.js documents ahead-of-time static modules; pin compatible CLI/runtime releases, retain generated source and notices, and record a reproducible generation command after checking that release's CLI. Do not parse schemas or generate JavaScript during a visitor run. [Official project code-generation documentation](https://github.com/protobufjs/protobuf.js#using-the-command-line), [project license](https://raw.githubusercontent.com/protobufjs/protobuf.js/master/LICENSE)
8. Omit default-valued singular fields from the object passed to the Protobuf encoder: empty name/email and zero age. Preserve empty strings inside hobbies. Decode into a fresh Person with absent scalar defaults restored and an absent hobbies collection restored as `[]`. Compare values field by field and hobbies in order, not object identity, JSON key order, or scalar-presence identity. Proto3 implicit scalar presence cannot distinguish an omitted default from an explicitly set default. Explain this qualification beside a passing round-trip result. [Proto3 defaults and presence](https://protobuf.dev/programming-guides/proto3/#default)

The comparison is compact JSON versus binary Protobuf for this schema. It is neither ProtoJSON nor compressed HTTP size. Show both decoded records and exact byte counts. Do not mark either format as the winner or require one to be smaller. Do not use timing as a completion condition. The article's historical Go benchmark and its large byte totals are not browser measurements; their editorial verification is separate work outside this file's authority.

## Minimum shared request and result contract

Put the contract and evaluator under `apps/timsexperiments/src/scripts/playgrounds/`. The HTML component owns draft state, focus, and live announcements. One trusted evaluator owns validation, normalized input, both encodings, decoding, and checks. The scene receives an immutable result snapshot through its integration owner. It never serializes the record itself or estimates results from text length. Use a callback or controller method in one page, not a global event channel.

The challenge registry contains the stable IDs above, title, instructions, starter record/JSON, fixed schema, worked explanation, limits, and expected check IDs. Frontmatter and scene configuration reference IDs only. Registry version changes when schema, normalization, limits, or measurement rules change. Request and response parsing must reject unknown protocol versions or challenge/version pairs.

A run request has `protocolVersion: 1`, `runId`, `challengeId`, `challengeVersion: 1`, and `inputJson`. The host creates a fresh monotonically increasing run ID per mounted challenge. All messages are size-bounded and validated at the receiving boundary. Visitor data never selects a Worker URL, module, driver, or schema.

Use a discriminated state with these variants. Common identity fields are `protocolVersion`, `runId`, `challengeId`, and `challengeVersion`. Use a positive integer run ID for a run; only idle may use `runId: null`. Byte lengths are nonnegative integers. Validate complete variant shapes rather than accepting arbitrary optional fields:

- `idle`: no result, used initially and after editing or reset.
- `running`: the current request is being processed; expose Stop.
- `completed`: include `schemaId`, `measurement: "browser-js-compact-json-vs-protobuf-binary"`, normalized `input`, `json` and `protobuf` records, and the three checks below. Each encoding record has `byteLength` and normalized `decoded`. JSON also has its exact compact `text`. Optional bounded byte previews are presentation only and never the source of byte counts.
- `invalid`: include field-addressed issues with stable code, path, and text. Use `$` for whole-document syntax/size issues. Return at most 16 issues, each with text bounded to 1 KiB. No byte counts or passed checks.
- `failed`: include a bounded error code and safe text for initialization, encode/decode, timeout, or protocol errors. No successful measurements.
- `cancelled`: no measurements, used after Stop. Reset returns to idle instead.

A completed run contains exactly `json-roundtrip`, `protobuf-roundtrip`, and `encodings-agree`. Each check has `id`, `status: "pass" | "fail"`, and readable detail. The first two compare each normalized decoded record to input; the third compares both decoded records. Keep a mismatch as completed with a failed check so diagnostic decoded values remain visible. Call the exercise passed only when all three pass. Inadmissible input is a validation error, not a successful encoding or guessed loss report. A size advantage is never a check.

Default first-stage execution uses a new module Worker for the trusted evaluator per Run, with a proposed five-second startup timeout and two-second evaluation timeout after readiness. The Worker improves cancellation and responsiveness; it is not an isolation claim. Terminate it on completion, failure, Stop, Reset, replacement, or component disposal. Accept only messages belonging to the current run; late readiness, result, and error messages must not replace newer state. One active run per mounted challenge. Bound the serialized response to 128 KiB before posting; fail instead of truncating decoded records. Bound error text to 1 KiB and attach no stack traces or input to telemetry.

The DOM always exposes byte counts and check details. The 3D instrument consumes only a current completed snapshot. Both ribbons use a common linear scale based on the larger byte count, with exact labels. Represent zero as zero length with its label still readable; do not invent a visible minimum that misrepresents size. On draft change, invalid input, cancellation, or failure, clear the old ribbons/readouts or explicitly label them stale and disable comparison. Prefer clearing for stage one. Animation is decorative, can be paused, and disappears under reduced motion. When no scene is mounted, the evaluator and HTML still work.

## Binary acceptance gate for stage one

These checks are requirements for the implementer, not tests passed by this research task:

1. A direct article URL and `#challenge` reach the challenge without loading Three.js or entering `/campus`. With JavaScript disabled, the article, fixed schema, starter, and worked explanation remain readable. Worker startup failure leaves those available with a recoverable message.
2. The introductory sample produces 107 UTF-8 JSON bytes and 68 binary Protobuf bytes under the rules above, with all three checks passing and the emoji intact. These are reference fixture expectations calculated from compact JSON and wire-format arithmetic, not results of an installed serializer or browser run. Verify the generated encoder against an independently reviewed full wire-byte fixture before accepting these numbers. The Protobuf string fields use length-delimited wire encoding. [Wire-format reference](https://protobuf.dev/programming-guides/encoding/#length-types)
3. The all-default record produces 43 JSON bytes and zero Protobuf bytes with all checks passing after default restoration. Zero-length Protobuf is a valid result, not a failure. Empty hobby entries, repeated hobbies, non-ASCII text, combining text, and int32 endpoints survive. Confirm -1 uses the article's `int32` encoding, not `sint32` ZigZag. [Signed integer wire encoding](https://protobuf.dev/programming-guides/encoding/#signed-ints)
4. Fixtures reject malformed JSON, arrays/null, missing/unknown fields, wrong types, fractional/out-of-range ages, lone surrogates, and each over-limit input. Exact boundary inputs pass. A deliberately mismatched decoder fixture fails the appropriate checks; test-only injection must not become a visitor-selectable encoder.
5. Editing fields or JSON changes the actual encoded output. Equivalent formatting or escaped-Unicode spelling yields the same normalized record and bytes. Both form views preserve drafts according to the rules above. A new invalid edit never leaves previous results labeled current.
6. Stop, Reset, replacement runs, startup failure, and navigation terminate pending work. A deliberately delayed test worker proves old results cannot reappear. A valid second run succeeds after cancellation and failure. Unmount/re-enter ten times without accumulating workers or listeners. This tests the trusted runner lifecycle, not arbitrary-code isolation.
7. Capture browser requests with the scene disabled. Apart from self-hosted static challenge assets, a run sends no data or execution request over the network. Use fixtures for existing subscription/analytics integrations and do not submit forms. Render input and error strings as text; an HTML/script-looking name must display literally.
8. Keyboard-only users can edit, switch views, run, stop, reset, and leave the challenge. Inputs have visible labels and associated errors. A polite live region announces completion/failure once without moving focus or speaking every decoded value. Test a real screen reader, 320 CSS-pixel layout, enlarged text, and reduced motion. Camera shortcuts are inactive while editing. Do not claim accessibility from semantic markup alone.
9. A campus adapter, when connected, displays the same current counts/checks and proportional ribbons. Graphics failure, pause, or reduced motion must not cancel a valid HTML task or hide output. The first direct-link-only campus slice can defer ribbons; it cannot claim the instrument-result gate passed until this adapter is exercised.
10. Run root `bun run check`, `bun run build:site`, and `bun run test --filter=apps-timsexperiments` after authorized dependency setup. Record failures against baseline. Test the built Worker bundle in Chromium, Firefox, and Safari with exact versions recorded. Agree device/browser support before release; untested browsers cannot be called supported. Follow the build plan's separate scene performance budgets when embedding the instrument.

## Arbitrary-code expansion gate

If editable JavaScript is required, add it as a separately labeled mode after stage one, feeding the same normalized Person and result contract. Do not quietly relabel editable JSON as arbitrary code support.

The research candidate remains synchronous QuickJS WASM inside a disposable Worker, with a fresh runtime/context per run and no guest host bindings for fetch, DOM, storage, filesystem, module loading, or timers. QuickJS's wrapper provides memory/stack limits and interruption hooks but explicitly says it has not been audited. This is a candidate capability boundary requiring implementation review and adversarial tests, not demonstrated secure isolation. [Wrapper runtime documentation and security status](https://github.com/justjake/quickjs-emscripten)

Proposed expansion limits are 64 KiB source, 32 MiB guest allocation, a configured stack limit, a two-second execution deadline plus startup timeout, and 16 KiB guest output. The outer Worker must still be terminable. Guest allocation limits do not bound browser memory, WASM overhead, host copies, or returned serialization. Extract only bounded plain JSON inside the guest, validate it again outside, and never execute returned functions/getters in the host. Pin interpreter/WASM artifacts and licenses before testing.

Before enabling this mode, prove infinite-loop interruption, allocation exhaustion, output flooding, import rejection, guest fetch/storage/DOM denial, bounded result conversion, Stop/Reset races, repeat-run recovery, and no challenge-triggered outbound requests after asset load. Inspect actual Worker response policy and WASM delivery under the intended CSP. Keep native eval disabled; determine the precise WASM policy from the pinned build. These checks can catch regressions but do not constitute a security audit. [CSP specification](https://www.w3.org/TR/CSP3/)

A plain Worker running visitor `eval` or `new Function` is not the fallback: Worker globals retain browser capabilities, and termination is not a network/capability policy. [Worker global interfaces](https://html.spec.whatwg.org/multipage/workers.html#worker-globals-and-functions)

WebContainer is not the zero-cost production default. Its official commercial guidance requires licensing for production for-profit use serving prospective customers; prototypes are exempt. This site's client-acquisition use makes license eligibility unresolved, so do not choose it without a zero-cost applicable license determination. [Commercial usage guidance](https://webcontainers.io/enterprise)

HTML/CSS previews, Python/WASM, Go/C#, package managers, terminals, and devcontainers each need a separate capability, licensing, payload, and accessibility proposal. None blocks the fixed serializer challenge.

## Exact blockers and unresolved choices

There is no identified external-service or secret prerequisite for stage one. Planning is complete enough to start the proposed bounded implementation once assigned. The following prevent claiming it implemented or release-ready today:

- Dependencies are absent, and no protobuf version, generated serializer, independent wire fixture, or Astro Worker build has been installed/tested. This task expressly prohibits installs, app edits, and servers, so those gates were not attempted.
- Browser/device support is unconfirmed. No browser run, screen-reader check, timing measurement, network capture, or lifecycle verification has occurred. Device selection blocks a support/performance claim, not writing the first implementation.
- Parent/user adoption of editable-data-first remains unresolved. If arbitrary JavaScript is required in the first slice, QuickJS delivery, CSP behavior, capability restrictions, resource limits, and hostile-input tests become blocking work for that mode. Never substitute native eval to meet that deadline.
- Shared article schema/layout/frontmatter ownership needs assignment before integration edits. The proposed IDs and protocol need parent/integration-owner adoption before separate challenge and scene implementations diverge.
- The historical Go benchmark's totals remain editorially unverified. They do not block a correctly labeled new browser example; they block reusing those totals as live results or using this challenge to validate the historical claim.

Saving progress, extra languages, camera choice, client-service wording, and a full terminal remain product questions for later stages. This continuation changed only `docs/planning/article-playgrounds.md`; the other campus plans and application source were read, not rewritten.
